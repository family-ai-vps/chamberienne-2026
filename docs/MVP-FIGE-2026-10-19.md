# La Chambérienne 2026 — MVP figé (19 octobre 2026)

**Statut : MVP de démonstration, non opérationnel pour la course.** Cette page décrit ce qui existe réellement, sans anticiper la synchronisation future.

- Sauvegarde immuable de travail : branche `backup/mvp-2026-10-19` pointant sur ce commit (ne pas la modifier).

## Architecture effective du MVP
- Application mono-page : `index.html` (~127 ko de texte), CSS et JavaScript intégrés ; données de démonstration intégrées à `const DATA`.
- `manifest.webmanifest` et icônes dédiées iPhone ; affichage manifeste `browser`. Aucune synchronisation multi-appareil ni serveur métier.
- Trois modes accessibles depuis le même sélecteur : **Bureau central**, **Responsable de secteur**, **Bénévole**. **Le sélecteur n'est pas une authentification ni un contrôle d'accès.**
- État opérationnel dans `localStorage` de l'appareil : pointages, statuts, incidents, renforts, matériel, consignes, infos course, historique et numéros d'appel configurés.
- Export HTML local d'une copie de l'état ; ce n'est ni une sauvegarde centralisée ni une procédure de reprise validée.
- Données de démonstration : **245 personnes, 78 postes, 287 affectations, 15 secteurs** ; **178 missions avec horaires explicitement simulés**. Ne pas les utiliser comme affectations 2026.
- Notifications push, synchronisation, identification personnelle, gestion des conflits et horodatage serveur : **non implémentés**.

## Parcours et comportements à conserver
- Bureau central : vue d'ensemble, annuaire et filtres, postes, accueil, renforts, incidents et clôture, matériel, consignes, infos course, journal.
- Responsable : secteur, équipe, demande de renfort, signalement d'incident, consignes et infos course.
- Bénévole : choix d'un nom, missions, confirmation de présence sur poste, équipe, informations.
- Recherche annuaire et postes : **validation par Entrée ou bouton « Rechercher »**, jamais à chaque frappe (clavier iPhone).
- Choix du bénévole : tri alphabétique du **nom de famille**, affichage « Prénom Nom ».
- Incident : description **non vide**, sans minimum de huit caractères ; visible dans les menus Incidents sur **le même appareil** ; clôture réservée au mode Bureau central.
- Secours FFSS : bouton **rouge** ; organisation : bouton **jaune**. Les numéros doivent être configurés et vérifiés avant usage.
- Les informations saisies sur un téléphone **ne remontent pas** aux autres téléphones.

## Audit technique — constats
1. **Critique — absence de synchronisation** : `localStorage` local ; aucun poste central ne peut recevoir les actions d'autres téléphones.
2. **Critique — absence de contrôle d'accès** : changement de rôle libre ; les rôles affichés ne constituent pas une protection.
3. **Critique — données réelles et confidentialité** : dépôt public, application cliente inspectable ; aucune donnée nominative réelle ni secret serveur à intégrer dans HTML/JS.
4. **Élevé — conflits / hors ligne** : pas d'ID d'opération durable, horodatage serveur, accusé de réception, résolution de conflits ni file d'attente synchronisée.
5. **Élevé — pointage / matériel** : opérations locales, pas de verrouillage transactionnel ; double remise de matériel et doubles pointages possibles sur plusieurs appareils.
6. **Élevé — robustesse PWA iOS** : cache et comportement « ouvrir comme app web » variables ; pas de stratégie de mise à jour contrôlée ni de test multi-iPhone.
7. **Moyen — maintenabilité** : CSS cumulatif (plus de 200 déclarations `!important`), HTML/CSS/JS dans un fichier, reconstruction complète du contenu par `render()`, données mêlées à la logique.
8. **Moyen — performances** : filtres et tris sur l'ensemble des personnes ; recalculs à chaque rendu. Faible charge actuelle mais à structurer avant données réelles.
9. **Moyen — dette de code** : ancienne logique de rafraîchissement de recherche et de restitution du focus inutilisée depuis le passage à la validation par Entrée ; nettoyage effectué **uniquement sur branche dev**.
10. **Moyen — tests** : pas de suite navigateur automatisée du MVP initial ; tests statiques ajoutés sur branche dev, insuffisants à eux seuls pour garantir l'absence de régression.

## Stratégie de non-régression
- Le commit MVP et sa branche de sauvegarde sont intacts.
- Sur `dev/post-mvp-audit-2026-10-19` : suppression du code mort de recherche/focus, mise en cache du tri de la liste des bénévoles ; données intégrées inchangées.
- `tests/mvp-smoke.mjs` contrôle : syntaxe JavaScript, volumes de données, unicité des ID, structure des missions, couleurs des boutons, recherche sur validation, présence des modules et suppression du code mort.
- Workflow GitHub Actions `Tests MVP` sur la branche dev. **Un test statique réussi ne prouve pas la non-régression fonctionnelle** ; recette manuelle sur Safari iPhone et PWA installée obligatoire avant fusion.
- Scénarios de recette à valider sur 2 appareils : trois rôles ; recherches et clavier ; pointage ; statut ; incident + clôture ; renfort ; matériel ; annonces ; export/restauration ; retour arrière ; cache PWA. La synchronisation inter-appareils est **attendue absente** pour le MVP.
